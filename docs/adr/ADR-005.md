# ADR-005: systemd-resolved as the required DNS resolver interface

**Status:** Accepted
**Date:** 2026-03-01

---

## Context

DNS leak detection requires reading, per interface, two distinct pieces of
information: the set of DNS servers *configured* for that interface, and the
single server that the resolver is *actively using right now*.  These two
values are not the same thing.  When a VPN is active, the configured servers
on a physical interface remain unchanged -- they are still the DHCP-assigned
addresses from the ISP or local router -- but the resolver shifts query
activity to the VPN interface.  A tool that reads only configured servers
would classify every dormant physical interface as a leak the moment a VPN
connects.  A tool that distinguishes configured from active can correctly
identify the dormant interfaces as having stepped aside.

Linux systems use several different name resolution stacks, and they do not
all expose per-interface DNS state in the same way:

**`/etc/resolv.conf` (static or managed by resolvconf/openresolv):** A flat
file containing a single `nameserver` list for the whole system.  There is no
per-interface view and no concept of a "current" vs "configured" server.
Whichever interface last wrote to the file wins; the others are invisible.
DNS leak detection against this model reduces to reading the file -- which
gives no information about which interface is responsible for the entry or
whether it is currently active.

**`dnsmasq`:** A caching forwarder that can be configured per-interface via
DHCP hooks.  Its configuration is spread across files in `/etc/dnsmasq.d/`
and is not queryable at runtime in a structured way without root (reading
`/run/dnsmasq/` or using `--local-service` modes).  Per-interface state is
not exposed through a stable, unprivileged API.

**`systemd-resolved`:** A system service with a D-Bus and CLI API.
`resolvectl status <interface>` returns structured output that includes both
`DNS Servers:` (the configured list) and `Current DNS Server:` (the
currently active server) for each interface independently.  This is the only
DNS stack on Linux that exposes the configured-vs-active distinction through
an unprivileged, per-interface, stable CLI.

---

## Decision

netcheck requires `systemd-resolved`.  All DNS state is read via
`resolvectl status <interface>`.  No other DNS resolver stack is supported.

The two fields extracted per interface are:

- `DNS Servers:` -- every server address systemd-resolved has received for
  this interface (typically via DHCP or static configuration).  Stored as
  `DNSConfig.servers`.
- `Current DNS Server:` -- the single address systemd-resolved is actively
  routing queries through for this interface, or `None` when the interface
  has stepped aside.  Stored as `DNSConfig.current_server`.

The `current_server` field is what makes accurate leak detection possible.
When a VPN is active, `current_server` on physical interfaces becomes `None`
because systemd-resolved has shifted the active designation to the VPN
interface.  The tool classifies these interfaces as `DORMANT` -- a positive
security signal meaning DNS isolation is working -- rather than treating the
absence of an active server as a leak.

---

## Consequences

**Positive**

- The configured-vs-active distinction is available and reliable.  Leak
  detection can correctly distinguish a dormant interface from a leaking one;
  false positives are structurally impossible for this class of error.
- `resolvectl` is an unprivileged CLI available on all target systems.  No
  root, no D-Bus library dependency, no parsing of internal state files.
- The output format of `resolvectl status <iface>` is stable across the
  systemd versions shipped by Debian 13 (Trixie) and later.
- The dependency is already present on target systems: `systemd-resolved` is
  enabled by default on Debian 13 (Trixie) and its derivatives, including
  Linux Mint LMDE 7.

**Negative / trade-offs**

- Systems using `resolvconf`, `openresolv`, `dnsmasq`, or a static
  `/etc/resolv.conf` are not supported.  The tool will fail to retrieve DNS
  state on these systems and will report `UNAVAILABLE` for all DNS fields
  rather than producing incorrect results.
- NixOS, Arch Linux, Alpine, and other distributions that do not enable
  `systemd-resolved` by default are excluded unless the user explicitly
  enables it.
- Any DNS traffic that bypasses systemd-resolved entirely -- such as a process
  that opens a raw UDP socket to port 53, or a DNS-over-HTTPS library with a
  built-in resolver -- is invisible to this tool regardless of the resolver
  stack in use.  This is a fundamental limitation of configuration-based
  detection, not specific to systemd-resolved.

**Excluded configurations**

| Resolver stack | Excluded | Reason |
|---|---|---|
| `systemd-resolved` | No -- required | Provides per-interface configured/active distinction |
| `resolvconf` / `openresolv` | Yes | No per-interface active-server API |
| `dnsmasq` (standalone) | Yes | No unprivileged per-interface runtime query API |
| Static `/etc/resolv.conf` | Yes | System-wide only; no per-interface view |

# ADR-003: Configuration-based DNS leak detection

**Status:** Accepted
**Date:** 2026-03-01

---

## Context

A "DNS leak" occurs when DNS queries escape the VPN and reach the user's ISP
resolver, meaning the ISP can observe which domains the user visits even while
the VPN is active.  A tool that claims to detect DNS leaks must define what
it actually measures and be honest about what it cannot.

There are two general approaches to DNS leak detection:

**Timing-based (active probing):** Send DNS queries from the tool itself and
measure which server responds, or use a dedicated leak-detection service
(e.g. dnsleaktest.com).  This reveals where queries actually go in practice,
but it requires making network requests as part of the tool, it is affected
by DNS caching, it is slow (one round-trip minimum), and it requires either
an external service or a self-hosted server.

**Configuration-based (passive inspection):** Read the DNS configuration from
the OS name resolver and classify the configured server based on known
categories.  This is fast, deterministic, requires no network requests beyond
what the tool already makes, and is completely reproducible -- the same system
state always produces the same classification.

netcheck uses systemd-resolved as its name resolver interface on all supported
systems (Debian 12 and later; systemd-resolved is the standard resolver on
these platforms).  `resolvectl status <iface>` provides both the configured
server list (`DNS Servers:`) and the server currently active for that
interface (`Current DNS Server:`).

---

## Decision

DNS leak detection is configuration-based.  The tool classifies each
interface's `Current DNS Server` by comparing it against three categories:

1. **ISP DNS** -- servers reported by physical interfaces (ethernet, wireless,
   cellular, tether), derived from their `DNS Servers:` list.  These are
   typically assigned by DHCP from the ISP or local router.
2. **VPN DNS** -- servers reported by VPN interfaces.  These are assigned by
   the VPN provider.
3. **Public DNS** -- a fixed list of well-known public resolvers: Cloudflare
   (1.1.1.1, 1.0.0.1), Google (8.8.8.8, 8.8.4.4), and Quad9 (9.9.9.9,
   149.112.112.112), plus their IPv6 equivalents.  This list lives in
   `src/netcheck/config/__init__.py` as `PUBLIC_DNS_SERVERS`.

The `Current DNS Server` field is used for classification, not `DNS Servers`.
This distinction is essential: when a VPN is active, systemd-resolved shifts
the `current_server` designation to the VPN interface.  Physical interfaces
remain *configured* with their original servers but are no longer *active*.
Classifying by `current_server` means a dormant physical interface is not
reported as a leak; classifying by `servers` would produce false positives on
every physical interface whenever a VPN is running.

The resulting statuses are:

| Status | Meaning |
|---|---|
| `NOT_APPLICABLE` | No VPN is active; leak analysis does not apply |
| `DORMANT` | VPN is active; this interface has correctly stepped aside |
| `OK` | Active server is a known VPN DNS server |
| `PUBLIC` | Active server is Cloudflare, Google, or Quad9 |
| `LEAK` | Active server is a known ISP DNS server |
| `WARN` | Active server does not match any known category |

The timing-based approach was considered and rejected for the following
reasons: it would require either an external service dependency or a
self-hosted test server; it is non-deterministic (caching can cause the same
configuration to produce different results on successive runs); it adds latency
to every tool invocation; and it measures a different thing (actual query path
under current caching state) than what the tool displays (the configured DNS
state, which determines where future uncached queries will go).

---

## Consequences

**Positive**

- Detection is instantaneous: no additional network requests are made.
- Results are deterministic: the same system state always produces the same
  classification.
- The tool works offline for all fields except the egress IP/ISP/country
  lookup, which is already clearly the only network-dependent step.
- The algorithm is fully unit-testable with fake `resolvectl` output; no
  network environment is required to test any leak classification scenario.

**Negative / trade-offs**

- The tool only covers DNS traffic routed through systemd-resolved.  A process
  that bypasses systemd-resolved and speaks DNS directly (e.g. by hardcoding
  `8.8.8.8` in `/etc/resolv.conf` or using a DNS-over-HTTPS library) is not
  visible to this tool.  This is a fundamental limitation of any
  configuration-based approach on Linux.
- The `PUBLIC_DNS_SERVERS` list in `src/netcheck/config/__init__.py` is static.
  New public resolvers are not detected until the list is updated.  An unknown
  server is classified as `WARN` rather than `PUBLIC`, which is the
  conservative failure mode (it prompts investigation rather than silently
  passing something unknown).
- ISP DNS and VPN DNS reference sets are derived from the current system
  configuration.  On a freshly connected interface whose DHCP-assigned servers
  have not yet been populated, or on an interface using servers not visible to
  `resolvectl`, the classification may be `WARN` rather than `LEAK` or `OK`.
  This is again the conservative failure mode.

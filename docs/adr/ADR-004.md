# ADR-004: `.pth` installation over pip packaging

**Status:** Accepted
**Date:** 2026-03-01

---

## Context

Netcheck needs to be installable on a development machine without requiring
root, without polluting the system Python installation, and without introducing
a build step that produces a wheel or sdist.  The project is a single-host
diagnostic tool, not a library intended for wide distribution.

The standard Python packaging mechanism -- `pip install .` -- requires either
a `setup.py` or a PEP 517 build backend (e.g. `setuptools`), and installs a
wheel into the target environment.  This creates two artefacts: an installed
package record (accessible via `importlib.metadata`) and the package files
themselves.  For a development tool that lives in a single cloned repository
and is modified in place, the wheel installation model is actively inconvenient:
every code change requires a reinstall, and the installed copy is a snapshot,
not the live working tree.

The conventional workaround for editable installs is `pip install -e .`, which
writes a `.pth` file or a `direct_url.json` pointer under the hood.  This
achieves the "live working tree" goal, but it still requires pip, still
registers an entry in `importlib.metadata`, and still demands that the Python
packaging metadata in `pyproject.toml` be kept aligned with pip's expectations
-- adding maintenance overhead for a tool that will never be published to PyPI.

A system-package constraint reinforces this choice: the declared runtime
dependency (`requests`) is installed via `apt`, not pip.  A project that mixes
apt-managed and pip-managed packages is brittle; pip may attempt to reinstall
or downgrade the apt-managed `requests` package if version constraints are
not carefully maintained.  The `.pth` approach avoids pip entirely and lets the
system package manager own all runtime dependencies.

---

## Decision

`make install` writes a single-line `.pth` file containing the absolute path
of the `src/` directory into the user site-packages directory
(`~/.local/lib/pythonX.Y/site-packages/netcheck.pth`).  Python's import
machinery reads `.pth` files at startup and adds each listed path to
`sys.path`, making `import netcheck` resolve to the live working tree at
`src/netcheck/`.

Writing `src/` rather than the project root eliminates the import-shadowing
hazard of the previous layout: with the project root on `sys.path`, bare
`import config` or `import utils` could accidentally resolve to the package
modules.  With `src/` on `sys.path`, only `import netcheck` works.

The launcher script (`bin/netcheck`) is copied to `~/.local/bin/netcheck` and
made executable.  It contains nothing but `from netcheck.__main__ import main`
and `sys.exit(main())`.

The version string is maintained manually in `src/netcheck/config/__init__.py` as
`VERSION = "X.Y.Z"` and is referenced from `pyproject.toml` via
`dynamic = ["version"]` and `version = {attr = "netcheck.config.VERSION"}`.

pip is not involved in installation or uninstallation.  `make uninstall`
removes the `.pth` file and the launcher; no package database is consulted.

To run the tool from the working tree without installing, use:

```bash
make run              # equivalent to: PYTHONPATH=src python3 -m netcheck
make run ARGS="-v"
```

---

## Consequences

**Positive**

- No build step.  `make install` runs in under a second and the installed
  tool immediately reflects any edit to the working tree.
- pip is not involved.  There is no risk of pip downgrading or replacing the
  apt-managed `requests` package.
- Uninstallation is two `rm -f` calls.  No package database entry to clean up.
- The Makefile is the single source of truth for installation logic.  No
  `setup.cfg`, no `MANIFEST.in`, no wheel build configuration.
- The `src/` layout eliminates accidental bare imports of package modules from
  the project root.

**Negative / trade-offs**

- `importlib.metadata` does not have an entry for netcheck.  Any code that
  calls `importlib.metadata.version("netcheck")` will raise `PackageNotFoundError`.
  The version must be read from `netcheck.config.VERSION` directly.  The
  `pyproject.toml` `dynamic = ["version"]` declaration exists to satisfy
  mypy and tooling that reads `pyproject.toml`; it does not imply a pip
  install.
- The `.pth` file contains the absolute path recorded at install time.  If
  the project directory is moved or renamed after installation, Python will
  silently fail to find the package on the next import.  There is no error at
  move time.  The fix is to re-run `make install` from the new location.  This
  limitation is documented in `README.md`.
- The version string in `src/netcheck/config/__init__.py` must be updated manually
  before each release.  There is no tooling that derives the version from a
  git tag or build system.  The update procedure is: edit `VERSION` in
  `src/netcheck/config/__init__.py`, commit, tag.

**Version update procedure**

A release is defined by steps 4 and 5 below -- the tagged commit.  Work
committed and pushed to GitHub before those steps is work-in-progress.
The `[Unreleased]` section of `CHANGELOG.md` accumulates in-progress
changes; `VERSION` in `src/netcheck/config/__init__.py` is bumped only at
release time, immediately before tagging.  The running binary always reports
the last tagged `VERSION`, regardless of what has been pushed since.

1. Edit `VERSION = "X.Y.Z"` in `src/netcheck/config/__init__.py`.
2. Update `CHANGELOG.md` with the release notes.
3. Run `make check` to confirm all tests pass.
4. Commit with message `release: vX.Y.Z`.
5. Tag the commit: `git tag vX.Y.Z`.

# ADR-006: `requests` over `urllib.request` for HTTP

**Status:** Accepted
**Date:** 2026-03-01

---

## Context

Netcheck makes two HTTPS GET requests per run: one to the ipinfo.io IPv4
endpoint and one to the IPv6 endpoint.  Both must handle transient network
failures gracefully -- the tool runs in environments where the network may be
briefly unavailable or rate-limited at the moment of the first attempt.

Python's standard library provides `urllib.request` for HTTP.  The `requests`
library is a third-party package that must be installed separately.  The
choice between them is not free: `requests` is an apt-managed runtime
dependency (`python3-requests`) that the user must have installed, and it
appears explicitly in `pyproject.toml` under `dependencies`.

The decision must be justified because adding any external dependency to a
tool installed via `.pth` (rather than pip) carries weight: the user is
responsible for keeping the dependency present and the tool has no way to
install it automatically.

---

## Decision

`requests` is used.  It is the sole runtime dependency that is not part of
the Python standard library.

The three specific capabilities that determined this choice are:

**1. Retry with exponential backoff.**  `SystemHttpClient` retries failed
requests up to a configurable number of attempts, sleeping
`backoff * 2**n` seconds between attempt `n` and `n+1`.  `urllib.request`
provides no retry mechanism; one would have to be written from scratch using
`urllib.error` exception types, a bare `time.sleep`, and manual loop
management.  `requests` provides a uniform `RequestException` base class
that covers every failure mode (connection error, timeout, TLS error,
redirect loop) in a single `except` branch, making the retry loop compact
and correct.

**2. Timeout handling.**  `requests.get(url, timeout=N)` applies the timeout
to both the connection phase and the read phase with a single argument.
`urllib.request.urlopen` accepts a `timeout` argument that applies to the
socket, but the semantics differ between Python versions for HTTPS and do
not cover the read phase uniformly.  A timeout that silently hangs on the
read phase is a user-visible failure mode for a diagnostic tool; `requests`
eliminates it.

**3. Response parsing and status checking.**  `response.raise_for_status()`
turns any non-2xx HTTP status into a `requests.HTTPError` (a subclass of
`RequestException`), which is caught by the same `except` branch as network
errors.  With `urllib.request`, non-2xx responses raise `urllib.error.HTTPError`
only for some status codes; others silently succeed and return a body that
must be inspected manually.  `response.json()` parses the body and raises
`ValueError` on malformed input, which netcheck catches explicitly.  The
equivalent with `urllib.request` requires reading the body, decoding it, and
calling `json.loads` separately -- more code, same result.

The `HttpClient` protocol (`src/netcheck/utils/http.py`) wraps `requests`
entirely.  No module outside `http.py` imports `requests` directly.  If the
dependency were replaced in the future, only `http.py` and its tests would
need to change.

---

## Consequences

**Positive**

- `SystemHttpClient` is 30 lines.  The retry loop, timeout, status check,
  and JSON parse each map to a single `requests` API call.  The equivalent
  `urllib.request` implementation would be roughly twice as long and require
  explicit handling of `urllib.error.URLError`, `urllib.error.HTTPError`,
  socket timeouts, and body decoding.
- `requests.RequestException` is a single exception hierarchy covering all
  network-level failures.  The `except` clause in `_single_attempt` is one
  line and provably exhaustive.
- The `HttpClient` protocol isolates `requests` from the rest of the
  codebase.  The egress module (`src/netcheck/network/egress.py`) has no import
  of `requests` and no knowledge of its error types.

**Negative / trade-offs**

- `requests` must be installed via `apt` before `make install` can produce
  a working tool.  The installation instructions in `README.md` include it
  explicitly: `sudo apt install python3-requests ...`.  A user who skips
  this step will get an `ImportError` at runtime.
- The minimum version is pinned to `>=2.32` in `pyproject.toml`.  This
  matches the version shipped by Debian 13 / Ubuntu 24.04 and is also the
  first release to fix CVE-2024-35195 (proxy credential leakage via session
  reuse).  Systems on older Debian/Ubuntu releases may have an earlier
  version installed; the tool will fail to import if the installed version
  is below this bound.
- `urllib3` (a transitive dependency of `requests`) emits debug log lines
  that appear in `netcheck -v` output alongside netcheck's own log lines.
  This is visible in the debug output and is documented behaviour, not a
  bug.

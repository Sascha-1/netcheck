# ADR-007: `StrEnum` over the `(str, Enum)` mixin pattern

**Status:** Accepted
**Date:** 2026-03-01

---

## Context

netcheck uses enumerations for all categorical domain values: interface types,
DNS leak statuses, egress statuses, and data field statuses.  Every one of
these values is also serialised as a plain string in JSON export and used
directly as a cell value in the table renderer.  The domain layer therefore
needs enum members that behave as strings without requiring callers to
explicitly access `.value`.

Python's `enum` module has supported this since Python 2 via the `(str, Enum)`
multiple-inheritance pattern:

```python
class InterfaceType(str, Enum):
    ETHERNET = "ethernet"
```

A member constructed this way is a `str` subclass.  Passing it where a `str`
is expected works at runtime -- `str(InterfaceType.ETHERNET)` yields
`"ethernet"` and equality with the literal `"ethernet"` holds.  However,
the pattern has two concrete problems in a codebase under mypy strict mode:

**Problem 1: `str()` coercion is required for clean type checking.**  mypy
treats `(str, Enum)` members as having type `InterfaceType`, not `str`.  A
function annotated to accept `str` will reject a `(str, Enum)` member unless
the call site wraps it in `str()`.  The silent runtime behaviour (it works)
diverges from the static type (it is wrong), which defeats the purpose of
strict type checking.

**Problem 2: `.value` access is the only mypy-clean comparison.**  Comparing
`InterfaceType.ETHERNET == "ethernet"` directly causes mypy to flag the
expression as a non-overlapping comparison between two `Literal` types.  The
comparison works at runtime but mypy rejects it under strict mode.  The idiom
to satisfy mypy is to widen the member to `str` before comparing -- or to
compare `.value` directly -- which adds noise at every call site.

Python 3.11 introduced `enum.StrEnum` as a first-class solution to both
problems.  `StrEnum` is defined in the standard library specifically to replace
the `(str, Enum)` pattern, and its semantics are designed to satisfy static
type checkers: a `StrEnum` member is typed as `str` by mypy, meaning it can
be passed anywhere a `str` is accepted without a cast or widening expression.

---

## Decision

All enumerations in `src/netcheck/core/enums.py` use `StrEnum` as their base
class.  The `(str, Enum)` mixin pattern is not used anywhere in the codebase.

```python
from enum import StrEnum

class InterfaceType(StrEnum):
    ETHERNET = "ethernet"
    VPN = "vpn"
    ...
```

Members compare equal to their string values after widening to `str`, which
is the correct mypy-clean idiom documented in `tests/unit/test_enums.py`:

```python
as_str: str = InterfaceType.ETHERNET
assert as_str == "ethernet"   # passes mypy strict; no .value needed
```

The JSON export layer (`src/netcheck/output/export.py`) and the table renderer
(`src/netcheck/output/table.py`) use enum members directly as strings: no `.value`
calls appear in either module.

`StrEnum` is available from Python 3.11 onwards.  `pyproject.toml` declares
`requires-python = ">=3.12"`, so the `StrEnum` requirement is covered by the
existing version constraint and does not introduce an additional lower bound.

---

## Consequences

**Positive**

- mypy strict accepts `StrEnum` members wherever `str` is annotated, with no
  cast or `.value` access required.  The divergence between runtime behaviour
  and static type that plagued `(str, Enum)` is eliminated.
- JSON serialisation and table rendering pass enum members through without
  conversion.  `dataclasses.asdict` serialises `StrEnum` members as their
  string values automatically.
- The `test_str_mixin_widens_to_str` tests in `test_enums.py` document and
  enforce the correct usage pattern: assign to `str`, then compare.  This
  keeps the tests consistent with how production code uses the enums.
- Construction from a string value (`InterfaceType("ethernet")`) works
  identically under `StrEnum` and `(str, Enum)`, so call sites that build
  enum members from parsed data are unaffected by the migration.

**Negative / trade-offs**

- `StrEnum` requires Python 3.11+.  This is not an additional constraint
  beyond what `pyproject.toml` already declares (`>=3.12`), but it means the
  enumerations cannot be backported to Python 3.10 or earlier without
  reverting to the `(str, Enum)` pattern or vendoring a compatibility shim.
- Direct equality comparisons between two enum `Literal` types (e.g.
  `InterfaceType.ETHERNET == InterfaceType.VPN`) are still flagged as
  non-overlapping by mypy, which is correct behaviour -- those comparisons
  are vacuously false and indicate a logic error.  This is a feature, not
  a regression.
- `StrEnum` values are always lower-case in this codebase by convention.
  A member whose name and value accidentally match (upper-case name, same
  lower-case value) would be caught by `test_name_and_value_are_distinct`
  in `test_enums.py`, which enforces the name/value distinction explicitly.

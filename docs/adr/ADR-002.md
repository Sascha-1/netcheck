# ADR-002: Frozen domain models and `dataclasses.replace`

**Status:** Accepted  
**Date:** 2026-03-01

---

## Context

`InterfaceInfo` and all its nested dataclasses (`DeviceInfo`, `DNSConfig`,
`EgressInfo`, `IPConfig`, `RoutingInfo`, `VPNInfo`, `ModemInfo`) form the
domain model of the tool.  The orchestrator builds these objects, the output
layer reads them, and nothing in between should modify them.

Two phases of the collection pipeline need to update records after initial
construction:

1. **DNS leak detection** (`check_dns_leaks` in `src/netcheck/network/dns.py`)
   -- computes a `DnsLeakStatus` for each interface, which requires a
   system-wide view of all interfaces (to identify VPN DNS and ISP DNS
   reference sets) before any single interface can be classified.  This
   cannot happen during per-interface construction.

2. **VPN underlay detection** (`_apply_vpn_underlay` in
   `src/netcheck/orchestrator.py`) -- identifies the VPN server endpoint from the
   routing table and the physical carrier by metric; then stamps both the
   carrier's `vpn.is_vpn_underlay` flag and every VPN interface's
   `vpn.server_ip` field.  Again, these are system-wide properties that
   cannot be known during per-interface construction.

The straightforward implementation of both phases is to mutate the records
in the list after construction.  The question is whether to allow this.

---

## Decision

All domain dataclasses use `frozen=True`.  Field mutation is a compile-time
error enforced by Python's dataclass machinery.

The two post-construction update phases use `dataclasses.replace` to produce
new objects with the changed fields, and replace the corresponding entries in
the working list.  The original objects are discarded.  The orchestrator
returns the final list; no reference to any intermediate state escapes.

```python
# Example from _apply_vpn_underlay
new_vpn = dataclasses.replace(iface.vpn, server_ip=server_ip)
result[i] = dataclasses.replace(iface, vpn=new_vpn)
```

The output layer receives the final list and never calls `dataclasses.replace`
or any other mutating operation.  It is a pure reader.

---

## Consequences

**Positive**

- The output layer can be passed any `InterfaceInfo` and trust that its fields
  will not change while it is rendering.  There is no need to defensively copy
  objects before passing them to a renderer.
- Tests can construct an `InterfaceInfo` and pass it to any function without
  worrying that the function will leave the object in a partially-updated
  state.  A frozen object in an unexpected state means the test fixture was
  wrong, not that a side-effect snuck in.
- mypy enforces immutability through the type system: any attempt to assign
  to a frozen dataclass field is a type error, caught before the code runs.
- The `dataclasses.replace` call sites are explicit and localised.  Every
  field update in the codebase is visible and grep-able.

**Negative / trade-offs**

- `dataclasses.replace` for deeply nested updates (e.g. updating
  `iface.vpn.server_ip`) requires two replace calls: one to produce a new
  `VPNInfo`, one to produce a new `InterfaceInfo` containing it.  This is
  more verbose than `iface.vpn.server_ip = server_ip`.
- Objects that hold large nested structures (not the case here, but relevant
  as the model grows) incur an allocation cost per update.  For the current
  scale (typically 4--8 interfaces per run) this is irrelevant.

**Boundary**

The immutability guarantee is intentionally limited to the domain model.
`_SharedRunData` in the orchestrator is also frozen, but it is an internal
scratchpad, not a domain object.  The working lists inside `check_dns_leaks`
and `_apply_vpn_underlay` are mutable Python lists; only the
`InterfaceInfo` objects they contain are frozen.

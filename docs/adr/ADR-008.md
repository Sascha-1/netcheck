# ADR-008: DataStatus on IPConfig and VPNInfo

**Status:** Accepted
**Date:** 2026-03-07

---

## Context

`IPConfig` and `VPNInfo` originally stored their primary data as bare
`str | None` fields: `ipv4`, `ipv6`, and `server_ip`.  `None` served as the
sole sentinel, conflating two structurally different outcomes:

- **`UNAVAILABLE`** -- the command ran successfully and returned output that
  contained no address (e.g. `ip addr show` succeeded but the interface has
  no address assigned).
- **`ERROR`** -- the command runner returned `None` because the subprocess
  failed, timed out, or was not found.

Downstream code -- the display layer and the JSON exporter -- cannot
distinguish these cases from `None` alone.  The table renderer must decide
whether to show `--` (unavailable) or `ERR` (error) for a field, but the
model gives it only a boolean: present or absent.  This violates
CONTRIBUTING.md Rule 2 (encode invariants in types, not prose): the
distinction between unavailable and error is a real semantic difference, and
collapsing it into a single `None` forces every consumer to either ignore the
distinction or recover it by duplicating the detection logic.

A parallel problem exists in the functions that populate these models.
`get_all_ipv4_addresses`, `get_all_ipv6_addresses`, and
`get_vpn_server_endpoint` all invoke `CommandRunner.run()`, which returns
`None` on failure and a string (possibly empty) on success.  An empty string
from a successful command is semantically `UNAVAILABLE` -- the command ran,
found nothing, and that is a normal outcome.  Checking `if not output:` treats
an empty string and a `None` identically, misclassifying a successful
command-with-no-results as a runner failure.  This bug is non-obvious and easy
to re-introduce because the falsy check looks correct at a glance.

Three connected decisions were made to address these problems.  They are
documented together because they form a single coherent design that is not
fully intelligible if any one piece is read in isolation.

---

## Decision

### 1. Apply `DataStatus` to `IPConfig` and `VPNInfo`

`IPConfig` gains `ipv4_status: DataStatus` and `ipv6_status: DataStatus`.
`VPNInfo` gains `server_ip_status: DataStatus`.  Each field holds one of:

- `OK` -- the corresponding data field is present and valid.
- `UNAVAILABLE` -- the query succeeded but returned no data.
- `ERROR` -- the runner failed; the data field is meaningless.
- `NOT_APPLICABLE` -- the field does not apply to this interface type by
  design (e.g. `server_ip` on a non-VPN interface).

Factory methods enforce the invariant in the type:

```python
IPConfig.ok(ipv4, ipv6)      # ipv4 must not be None
IPConfig.unavailable()       # ipv4 and ipv6 are None; status is UNAVAILABLE
IPConfig.error()             # ipv4 and ipv6 are None; status is ERROR
```

Constructing `IPConfig` with `status=OK` and `ipv4=None` raises `ValueError`
at construction time.  The invariant is encoded in code, not prose.

The display layer and JSON exporter read the status field directly and choose
their rendering without any inference from `None`.  A `DataStatus.ERROR`
status maps to `ERR`; `DataStatus.UNAVAILABLE` maps to `--`.  No
reconstruction of intent is required.

### 2. Use `tuple[..., DataStatus]` rather than a named dataclass for function return types

`get_all_ipv4_addresses` returns `tuple[dict[str, str], DataStatus]`.
`get_vpn_server_endpoint` returns `tuple[str | None, DataStatus]`.

A named dataclass (on the model of `DeviceInfo`, `RoutingInfo`, etc.) was
considered and rejected.  The distinction is: a dataclass is appropriate when
the result is a *domain object with identity* that will be stored, passed
across module boundaries, and consumed by multiple callers over its lifetime.
`DeviceInfo` qualifies -- it is stored on `InterfaceInfo`, serialised by the
JSON exporter, and rendered by the table formatter.

A function-local transport pair -- data plus a status that travels together
only as far as the immediate caller -- does not qualify.  Introducing a
dedicated dataclass for `AddressResult` or `VpnEndpointResult` would add
named types to the public module surface purely to wrap values that are
destructured one call-site away.  The tuple form keeps the surface area
minimal: it is immediately destructured at the call site (`data, status =
get_all_ipv4_addresses(runner)`) and has no further API life.

The rule of thumb applied here: if the result type requires a name to be
understood -- if you would need to look up the class to know what the fields
mean -- it earns a dataclass.  If the pairing is obvious at the call site,
a tuple is correct.

### 3. Use `if output is None` to distinguish runner failure from empty output

`CommandRunner.run()` has the following contract:

- Returns `None` if the subprocess failed, timed out, or was not found.
- Returns a string (possibly empty) if the subprocess succeeded.

An empty string is not a failure.  `ip addr show` can succeed and produce no
`inet` lines if the interface has no address assigned.  The correct
classification is `UNAVAILABLE` -- the command ran, the interface exists, it
just has no address.  Checking `if not output:` treats an empty-string result
as `None`, misclassifying a successful no-results run as a runner failure and
producing `ERROR` where `UNAVAILABLE` is correct.

All code that populates `DataStatus` from a `CommandRunner` result checks
`if output is None` explicitly.  The empty-string case falls through to the
address-parsing branch, which produces an empty dict and returns
`DataStatus.OK` paired with that empty dict, which the caller maps to
`UNAVAILABLE` on the model.

---

## Consequences

**Positive**

- The display layer and JSON exporter can render `--` vs `ERR` correctly and
  unconditionally, without inferring meaning from absence.
- The `OK`-implies-data invariant is enforced at construction time; it cannot
  be violated by a caller that forgets to set the address when status is `OK`.
- The `if output is None` pattern makes the runner contract explicit at every
  call site; the distinction between empty output and a failed command is
  visible in the code rather than hidden in falsy evaluation.
- `DataStatus` already existed in `src/netcheck/core/enums.py` for `DeviceInfo`
  and `RoutingInfo`.  Applying it to `IPConfig` and `VPNInfo` extends a
  consistent pattern rather than introducing new vocabulary.
- The JSON export gains `ipv4_status`, `ipv6_status`, and
  `vpn_server_ip_status` fields, allowing programmatic consumers to distinguish
  unavailable data from error conditions without parsing display strings.

**Negative / trade-offs**

- Every call site that previously read `iface.ip_config.ipv4` must now also
  consult `iface.ip_config.ipv4_status`.  The model is more verbose to
  consume.  This is the intended trade-off: the additional verbosity is the
  cost of making the distinction explicit.
- The `NOT_APPLICABLE` variant of `DataStatus` does not currently apply to
  `IPConfig` or `VPNInfo` fields, but it is present on `DataStatus` for
  consistency with `DeviceInfo` and `RoutingInfo`.  Future fields that do not
  apply to all interface types can use it without changing the enum.
- Factory-method construction is slightly more ceremonial than direct
  `IPConfig(ipv4="...", ipv6=None)` assignment.  The ceremony is intentional:
  it forces callers to choose a status explicitly rather than relying on
  field-defaulting to produce a semantically ambiguous value.
